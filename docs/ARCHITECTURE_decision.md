# Which surfaces need a threshold at all?

The ignorance floor (0.3089) invalidated most of our operational numbers. But it
only matters where a **scalar cut** on the urgency score drives a decision. We
committed to ranking over filtering, and ranking is threshold-free — so the floor
may change very little about what we actually ship.

This enumerates every decision point, what each consumes, and therefore which
blockers genuinely bind.

Numbers regenerated by `ml/regenerate_report.py` from frozen test split
`ce6761fd5b40`; ignorance floor **0.3089**.

---

## 1. Decision points

| # | surface | consumes | threshold on urgency score? | floor relevant? |
|---|---|---|---|---|
| 1 | Queue ordering for human review | **rank only** | no | **no** |
| 2 | Entropy gate → "uncertain" | entropy | no | no |
| 3 | Escalation shown to the user | symptom gate only | no | no |
| 4 | OOD gate ("is this skin?") | Mahalanobis distance | no | no |
| 5 | Capture quality gate | sharpness / brightness | no | no |
| 6 | **Top-3 shortlist: show or withhold** | **max-class probability** | no (but a cut exists) | no |
| 7 | *User-facing urgency flag* | **urgency score** | **yes** | **yes** |

**Six of seven surfaces never threshold the urgency score.** Only #7 does — and #7 is
the surface we have already decided not to ship.

### Detail on each

**1 — Queue ordering.** A human reviews the top-k% by score. Rank is invariant to any
monotone transform, so the floor, the Platt scaling and the log-odds correction all
leave it *exactly* unchanged. Nobody is excluded; a low rank means "seen later", not
"never seen".

**2 — Entropy gate.** Thresholds normalised predictive entropy, a different quantity
from the urgency score. It routes diffuse predictions to "uncertain". Its own cut
(E≈0.70) needs justifying on its own terms, not against the floor.

**3 — Escalation.** Comes from `ml/symptom_gate.py`, which is rule-based,
model-independent and escalate-only. No model score enters it. This is deliberate:
the classes that most need escalation (cellulitis, systemic disease) are the ones the
image model ranks worst.

**4, 5 — OOD and quality gates.** Both threshold quantities unrelated to urgency
(feature distance; variance-of-Laplacian and mean luma). Unaffected.

**6 — Shortlist display.** Uses max-class probability to decide whether to show
anything at all. It is a scalar cut, but on a different quantity, and its failure mode
is showing a shortlist when it should say "unclear" — not a missed escalation.

**7 — User-facing urgency flag.** The only surface consuming a cut on the urgency
score. **Declared off** — `SURFACE_7_URGENCY_VERDICT = false` in `src/lib/surfaces.js`.

> ### ⚠️ This surface was FOUND LIVE in the codebase
>
> An earlier version of this document asserted surface #7 "is not shipping", and that
> assertion was used as the **premise** for the finding that Blocker 1 does not bind.
> It was wrong: `src/App.jsx` rendered an urgency band, named conditions and red flags
> from the LLM triage path (`runTriage` → `clinicalPrompt.js`) the entire time.
>
> **Was it in front of users?** No. The repo has no deployment configuration of any
> kind and is not under version control, so it has never been pushed anywhere; it runs
> only on localhost via `vite` and `node server/proxy.js`. That is verified for *this*
> repo on *this* machine — a copy deployed elsewhere would not be visible from here.
>
> **Now:** the render is behind the flag, and so is the `runTriage` CALL itself —
> gating only the render would have left the image going to a third-party API to
> produce output nobody sees.
>
> **Blocker 1's status depends on this flag staying off.** With it on, Blocker 1
> BINDS: 30.2% of benign pigmented lesions flagged at an above-floor threshold,
> measured on a corpus lighter-skinned than our users. The LLM path additionally has
> **no calibration and no per-tone characterisation at all**, which is worse than a
> measured 30.2%, not better.
>
> **Why it is off for the pilot, beyond the architecture argument:** a tester shown
> named conditions reacts to the diagnosis rather than to the capture flow, and may
> have their symptom answers contaminated by it. The pilot measures capture,
> questionnaire and firing rates; a verdict on screen degrades all three.

### Surface status is VERIFIED, not asserted

This was the third time an assumption in a document was used as a premise (after the
`fill=0.40` gate and the below-floor thresholds). Status is now three things:

| | |
|---|---|
| **declared** | a flag in `src/lib/surfaces.js` that the build actually reads |
| **rendered** | named code patterns per surface |
| **verified** | `ml/check_surfaces.py --check` — **exit 1** if a surface declared off is reachable |

Verified with a negative control: un-gating surface #7 fails the check; restoring it
passes. Run it in CI alongside `npm run test:conformance`.

## 2. Which blockers actually bind

### Blocker 1 — benign-pigmentation false alarms: **does not bind**

Its measurements are all flag-rate-at-threshold: 0.714 at t=0.12 (below floor),
0.302 at t=0.32. Both describe surface **#7**.

Under a ranking architecture the relevant question is different — *do benign pigmented
lesions crowd out the queue?* Measured:

```
benign pigmented capture at top-10%   0.037
```

Only **3.7%** of benign pigmented cases reach the top 10%. They occupy roughly 4–5%
of a 10% review queue. That is not a flood; it is a rounding error in reviewer time.

**Blocker 1 constrains a surface we have already decided not to ship, and nearly
vanishes under the one we did.** It should be recorded as *conditional on shipping an
urgency flag*, not as a blocker on the product.

*Caveat:* if the app ever shows a user-visible "this may be urgent" state, Blocker 1
binds immediately and hard.

### Blocker 2 — time-critical classes rank and recall worst: **binds directly**

This is the one that survives every architectural choice, because it is measured on
**rank**, which is what we ship:

```
capture at top-10%     cellulitis 0.260   bullous 0.257   AK/BCC 0.266
                       aggregate  0.330   melanoma 0.526
```

~3 in 4 cellulitis cases sit outside the top 10%. Moving above the floor makes the
threshold view worse too (cellulitis recall 0.918 → 0.685), but the ranking figure was
never threshold-dependent and does not improve.

**This is the binding constraint on the queue product**, and it is not fixable by
better ranking — cellulitis is diagnosed on spreading margin, warmth, fever and pain,
none of which are in a photograph. The mitigation is architectural, not modelling:
route it to `symptom_gate.py` (#3), which bypasses the model entirely.

### Blocker 3 (unnumbered until now) — **no brown-skin and no phone-photo evidence**: binds everything

Every number in this project — including all of the above — is measured on curated
atlas photography of a mostly light-skinned population, at a median source resolution
of 477px, with 97% of images in a single resolution bucket.

- `fairness_measurable: false` in every eval output. No per-skin-tone metric exists.
- The app's real input is phone photos, of which the current pipeline discards 99.6%
  of the pixels before inference.
- Distribution shift direction is almost certainly optimistic: models degrade under
  shift, they do not improve.

**This binds harder than Blockers 1 and 2 combined**, because it means we do not know
the true value of any figure we would act on. `ml/eval_holdout.py` exists to close it
and is waiting on images.

## 3. Conclusion

The reading that the floor changes little about what we ship is **correct**:

1. **Ranking is threshold-free.** The floor, calibration and score corrections do not
   touch the queue product at all.
2. **Blocker 1 is conditional**, on a surface we are not shipping, and largely
   dissolves under ranking (3.7% queue occupancy).
3. **Blocker 2 binds** and is architectural — the fix is the symptom gate, not the
   model.
4. **The absence of representative evidence binds hardest** and is unresolved.

### What follows

- Stop optimising the urgency threshold. It feeds one unshipped surface.
- Judge the binary head on **rank metrics** — per-class top-k capture, especially for
  time-critical classes — with flag rates secondary.
- Treat the holdout as the top priority. It is the only thing that converts any of
  this from provisional to real.

## 3b. PERMANENT CONSTRAINT — per-tone performance is not measurable

**Read this before proposing any triage feature.**

`ml/power_analysis.py`, from measured DermNet effect sizes:

| question | images needed at 80% power |
|---|---|
| per-tone urgent **recall** (light vs dark) | **17,804** |
| per-tone top-10% **capture** | **1,884,829** |
| per-rule-group symptom yield, cellulitis | 9,604 |
| per-rule-group symptom yield, SJS/TEN | 48,018 |

The driver is arithmetic, not analysis quality: per-tone metrics on rare outcomes
need *urgent cases within each tone group*, and a consumer app's ~5% urgent
prevalence multiplies the requirement twentyfold. **No amount of consumer-app data
collection reaches these numbers.**

### The rule that follows

> **No safety argument may depend on per-tone model performance**, because that
> quantity is not measurable at any sample size this project can reach. Any surface
> whose safety case requires per-tone recall is **out of scope by construction — not
> deferred**.

This is permanent unless a clinic-enriched study happens
(`docs/CLINIC_STUDY_spec.md`), which changes the prevalence and therefore the
arithmetic.

### What carries the safety case instead

1. **The symptom gate (`ml/symptom_gate.py`) is load-bearing.** It is rule-based,
   model-independent and escalate-only, so its behaviour does not vary with skin tone
   at all — there is no tone-dependent statistic in it. That property is what makes it
   usable when per-tone model performance is unknowable.
2. **The model is confined to ranking for human review**, where a miss means "seen
   later", not "never seen". Rank is threshold-free and the failure mode is delay.
3. **No user-facing urgency flag.** Already surface #7's status; now it is also
   unreachable, because its safety case would require exactly the metric we cannot
   measure.

**What is unknown about (1), and in which direction it fails.**

The gate's *yield* for time-critical groups is unmeasurable in a consumer pilot
(cellulitis 9,604 images; SJS/TEN 48,018). State the consequence precisely, because
"unvalidated" invites a reading the design rules out:

| | |
|---|---|
| **Unknown** | *How much* the gate helps — what fraction of true cellulitis or SJS/TEN it actually catches. |
| **Structurally guaranteed** | The gate is **escalate-only**. It can raise urgency and can never lower it, and it never suppresses an image-driven escalation. |

So unvalidated sensitivity fails toward **under-referral relative to the gate's
potential** — some cases it could have escalated, it does not. It cannot fail toward
harm, because **the floor is the no-app baseline**: a user who would have sought care
anyway is never told not to. The worst case is that the gate adds less than it could,
not that it subtracts.

That floor is a property of the escalate-only design, not of any measurement, which
is why it holds even though the sensitivity number does not exist. It is also the
reason a rule-based gate is the right load-bearing mechanism here — an ML-based one
would have no such guarantee.

The gap is still worth closing, and it is the strongest argument for the clinic
study. But it is a question of *how much benefit*, not *whether there is risk*.

### The gate exists in English only

The gate carries the safety case, and our users are vernacular Telugu/Kannada/Tamil
speakers. A mistranslation of *"peeling off in sheets"* (our lay proxy for Nikolsky)
is a safety defect of the same class as a wrong threshold — the rule silently stops
firing on the cases it exists for.

`docs/TRANSLATION_plan.md` specifies forward translation ×2, reconciliation,
independent back-translation, per-item scoring (equivalent / shifted / **lost**), and
comprehension testing with 5–8 target-population speakers per language. Any item
scored *lost* on a `tier: today` rule blocks that language from the pilot.

`capture_language` is recorded on every capture so a per-language firing-rate
difference is detectable. **Such a difference is a translation defect until proven
otherwise** — disease prevalence does not vary that sharply between neighbouring
language groups.

Run the English pilot first: it produces the firing-rate baseline the translated
versions get compared against.

### Measurable substitute, and what it is not

A **continuous** comparison of the urgency-score distribution between tone groups
(mean shift / KS / calibration by tone) detects a systematic depression of d=0.3 at
**349 images, or 174 paired within-subject**. That is achievable.

It is a **sensitivity signal, not a fairness guarantee** — equal score distributions
do not imply equal recall. It is included because it is the only tone metric in
reach, and it must never be reported as evidence of fairness.

## 3c. CONSTRAINT — closed-API LLMs have no clinical role, and never see images

Applies to Gemini or any other closed model API.

### Prohibited

| | |
|---|---|
| naming a condition | no differential, no shortlist, no "this looks like…" |
| asserting urgency | no tier, no "see a doctor soon", no risk language |
| generating or translating questionnaire wording | the 27 items and their translations are the safety mechanism |
| **receiving a photo** | no image egress to any third-party API |

### Why — and it is not the same argument as §3b

Everything in this document's blocker and floor framework depends on quantities we
can measure on a frozen split: an ignorance floor derived from the class structure,
a calibration temperature, per-tone flag rates, bootstrap CIs. **None of that
apparatus applies to a closed API.** It has no calibration we can fit, no per-tone
behaviour we can measure, no version we control, and no way to audit what changed
between one week and the next. A blocker cannot bind on it because there is nothing
to measure; a floor cannot be computed because there are no class marginals. It sits
entirely outside the framework rather than failing inside it.

That is *worse* than a measured 30.2%, not better — which is exactly the reasoning
that took surface #7 off.

**On questionnaire wording specifically:** `TRANSLATION_plan.md` requires two
independent professional translators, reconciliation, blind back-translation,
per-item scoring (equivalent / shifted / **lost**), and comprehension testing with
target-population speakers. A generated translation satisfies none of that, and the
items it would render include our lay proxy for Nikolsky sign — where a shift from
"peeling in sheets" to "dry and flaking" silently stops the rule firing.

**On images specifically:** sending a photo to a third-party API contradicts three
commitments already made. `CLINIC_STUDY_spec.md` promises images are stored on
institutional or partner-approved infrastructure and never publicly accessible. It
promises deletion on withdrawal — which we cannot honour for a copy sitting in
another company's logs. And the DPDP posture assumes we control where the data goes.
`withdraw()` can unlink our files; it cannot reach into someone else's retention.

### Acceptable later, and only after the pilot

- **Visit-prep text** generated from the user's *own symptom answers* — text in, text
  out, no images, no claims, restating what the user already told us.
- **Reader-assist in the labelling tool** — a dermatologist-facing convenience, where
  a qualified reader is the one making every judgement and can see the input.

Both are text-only, image-free, and make no clinical assertion. **Neither before the
pilot.**

## 4. Open questions in the record

### OPEN-1 — brown bin worse than dark bin (unexplained)

With the colour+edge localiser, centre-crop fallback by ITA bin:

| bin | n | fallback | 95% CI |
|---|---|---|---|
| very light | 676 | 0.124 | 0.10–0.15 |
| light | 356 | 0.157 | 0.12–0.20 |
| intermediate | 372 | 0.156 | 0.12–0.19 |
| tan | 530 | 0.172 | 0.14–0.20 |
| **brown** | **833** | **0.234** | **0.20–0.26** |
| **dark** | **1155** | **0.203** | **0.18–0.23** |

The gradient is not monotonic: **brown is worse than dark**, and their CIs barely
overlap, so this is unlikely to be small-n noise — both are the *largest* bins.

Ruled out so far:
- **not small-n** — brown (833) and dark (1155) are the two biggest bins
- **not exposure** — gradient survives excluding images with >2% clipped pixels
  (gap +0.076, CI [+0.041, +0.111])
- **not tight framing** — fallback correlates *positively* with framing tightness
  (+0.175), and the gradient persists in the widest-framed quartile

Still open: whether ITA is reading lesion darkness rather than patient tone
(`ml/ita_confound.py`). If the gradient collapses on clean perilesional samples, this
anomaly closes there and the whole finding needs relabelling.

**Status: OPEN.** Does not block — the reticle makes the localiser non-load-bearing —
but it means the residual tone gradient is not understood, only mitigated.

### OPEN-2 — residual tone gradient after the edge channel

Gap +0.079, **95% CI [+0.044, +0.112], excludes zero**. Real, not noise. Mitigated
rather than fixed: the reticle is tone-independent by construction, so the localiser
only refines when it agrees with where the user aimed.
